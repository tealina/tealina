# Create Tealina

The Tealina scaffold: a typed Node API server for Express, Fastify or Koa, where the
**each handler file is a route** and each **handler's type annotation is the
single source of truth** that the router, the API documentation and the frontend types
are all derived from.

The backend is three workspace packages with one job each, and the project compiles and
serves out of the box. Add `--web` for a minimal Vite frontend that reads the API types.

## ⚡ Quick Start

```bash
# Using pnpm
pnpm create tealina my-app

# Using npm
npm create tealina@latest my-app

# Using bun
bun create tealina my-app
```

You will be asked for a project directory and a server framework. The scaffold only writes
the project — it does not install dependencies or run anything in it. When it finishes:

```bash
cd my-app
pnpm install
pnpm -F api-v1 gdoc
pnpm dev
```

- Service: http://localhost:8000
- API documentation: http://localhost:8000/api-doc/index.html

### Flags

| Flag | Effect |
| --- | --- |
| `--template express\|fastify\|koa` | Skip the framework prompt |
| `--web` | Add `packages/web`, a minimal Vite frontend |
| `--integrate` | Write `INTEGRATION.md`, a merge playbook for an AI agent |

`--template` and a project name together make a run fully non-interactive:

```bash
pnpm create tealina my-app --template fastify --web
```

The scaffold asks before deleting an existing target directory, so a non-interactive
run must point at a new or empty directory.

### Requirements

Node ≥ 22 (the default is Node 24, recorded in `.nvmrc`), and pnpm 12.x for `pnpm install` —
the generated `package.json` declares `engines.pnpm`, and `pnpm-workspace.yaml` uses
`allowBuilds`, which older pnpm ignores. The scaffold never installs for you; it prints the
first commands and leaves them to the project.

The CLI needs TypeScript `>=5.6.2 <7` because it drives the Compiler API. TypeScript 7
is the Go-native rewrite and does not expose that API yet — 7.0.2 is not supported.

Only TypeScript is scaffolded. The recipe for keeping `.js` handlers in a TypeScript
project is [below](#-keeping-javascript-handlers).

## 📦 What You Get

```
my-app/
  package.json            scripts delegate to the three backend packages
  pnpm-workspace.yaml     backend/* and packages/*
  INTEGRATION.md          only with --integrate, an AI merge playbook
  backend/
    core/                 the contract layer
      types/              handler types, common shapes, the framework alias
      src/access/         openApi / authedApi, and the guard authedApi installs
    api-v1/               one API version
      src/api/            get/health.ts, post/login.ts, post/article.ts
      src/                router.ts, doc.ts, mount.ts
      version.js          API_VERSION and API_BASE_URL
      types/api.d.ts      the contract's exit point (exports["./api"])
      tealina.config.ts   apiDir / apiBaseURL / handlerImport / typesDir
      docs/api.json       generated by gdoc
    server/               the host
      src/                app.ts, doc.ts, index.ts, the static assets route
      public/             served by the static assets route
  packages/web/           only with --web
    src/
      main.ts             the page
      api/client.ts       `req`, typed from the handlers in api-v1
```

The dependency direction is `core → api-v1 → server`, and `web → api-v1`. Each package
publishes the seam the next one needs through its own `exports` map — there is no
`tsconfig` path setup to keep in step.

A second API version is a new package, `backend/api-v2`, that depends on `core` and is
mounted by `server` beside `api-v1`. Nothing in `core` or in the frontend names a version.
Each version publishes its own document json; the `server` package owns the single
documentation page and lists every version it mounts.

### Running the project

| Command | What it does |
| --- | --- |
| `pnpm dev` | Build `core` and `api-v1`, then start every watcher |
| `pnpm build` | Build all packages |
| `pnpm start` | Run the compiled server |
| `pnpm check` | Format, lint and type-check with Vite+ |
| `pnpm fmt` / `pnpm lint` | Run one half of `check` |
| `pnpm -F api-v1 <script>` | Run `create`, `align`, `gdoc`, `dev` or `build` in `api-v1` |

Each package exposes its own subset: `core` has `dev` / `build`, `server` adds `start`,
and `web` (with `--web`) has `dev` / `build` / `preview`. For CI, `align --check` and
`gdoc --check` exit non-zero when generated files are stale without writing anything; add
`--json` to get `{ ok, changed }` on stdout.

`POST /article` is the interesting endpoint: it is authenticated and carries both a
request body and a typed response, so it demonstrates the whole path from handler
annotation to frontend type.

Every endpoint requires an `Authorization` header by default. An endpoint makes itself
public where it is written, by ending its file in `openApi(handler)` instead of
`authedApi(handler)` — the same call that annotates the handler installs (or withholds) the
guard. The router holds no list of paths, so a new endpoint is private until you say
otherwise.

## ➕ Adding an endpoint

The method name and the filename are the method and the path:

```bash
pnpm -F api-v1 run create post/user # writes src/api/post/user.ts
pnpm -F api-v1 align                # rebuilds the generated index files
pnpm -F api-v1 gdoc                 # regenerates docs/api.json
```

The `index.*` files under `src/api/` are **derived artifacts**. Run `align` whenever
you add, rename or delete a handler by hand; never edit them directly.

## 🟨 JavaScript handlers

The scaffold writes TypeScript, but handlers can also be written in `.js`. A `.js` file is
compiled and checked beside the `.ts` ones, and the two can be mixed file by file.

1. Set `"allowJs": true` in every backend package's `tsconfig.json` and
   `tsconfig.build.json`. The scaffolds ship the same file in each package, but each one
   needs the flag: `server` resolves `api-v1/mount` through that package's `types` entry,
   which points at `src/mount.ts`, so the host compiles the route tree as well — a `.js`
   barrel with no `allowJs` there is TS7016.
2. In `api-v1` — the package that keeps the handlers — also add `"checkJs": true` to both
   files and `"src/**/*.js"` to `include` in `tsconfig.json`. The include patterns are
   explicit, so `allowJs` alone does not widen them. (The build config includes the whole
   `src` directory, so it needs only the flags.)
3. In `tealina.config.ts`, set `sourceExt: '.js'`. `create` then writes a JSDoc stub and
   `align` names its barrels `index.js`.
4. Annotate a handler through the published entry (or declare global aliases in
   `src/global.d.ts` to avoid repeating the import):

   ```js
   /**
    * @typedef {object} LoginPayload
    * @property {string} account
    */

   /** @type {import('core/handler').AuthedHandler<{ body: LoginPayload }, { token: string }>} */
   const handler = async (req, res) => {
     res.send({ token: 'JWT token' })
   }

   export default authedApi(handler)
   ```

5. The first `align` after switching writes `index.js` and leaves the previously generated
   `index.ts` beside it. Delete the `index.ts` barrels once — NodeNext resolves `./index.js`
   to `index.ts` before the real `.js`, so leaving both means the generated one wins and
   your new handler is invisible.

To finish the migration, rename handlers one at a time, then remove the flags and
`sourceExt` when no `.js` files remain. A frontend kept in JavaScript needs `allowJs` and
`checkJs` in `packages/web/tsconfig.json`; its `include` already covers `.js`.

## 🔗 Adding a frontend

```bash
pnpm create tealina my-app --web
```

You get a Vite project in `packages/web`, with no framework — no React, no router, no UI
library. Two source files, because what it demonstrates is not a UI, it is the client:

```ts
// packages/web/src/api/client.ts
import { createFetchClient } from '@tealina/client'
import type { ApiTypesForClient } from 'api-v1/api'

export const req = createFetchClient<ApiTypesForClient, RequestInit>(requester)
```

`ApiTypesForClient` is the handlers in `api-v1`, projected for a client. It arrives
through that package's `exports["./api"]` entry — one `workspace:*` dependency and one
`import type`, no code generation, no `tsconfig` paths, no project references, no build
step. **Rename a field in a handler and the frontend stops compiling**, which is the
point.

`src/main.ts` calls `GET /health` and renders the result. It is a placeholder: delete it
and write your app in `src/`. `vite.config.ts` proxies `API_BASE_URL` to
`localhost:8000`, which is why no server template sends CORS headers.

The flag is optional in every sense. A project scaffolded without it has no
`packages/web` at all, and adding a frontend later is a normal package that imports the
same types:

```ts
import type { ApiTypesForClient } from 'api-v1/api'
```

`import type` is required — that export carries a `types` condition only.

## 🔀 Integrating into an existing project

```bash
pnpm create tealina my-app --integrate
```

The flag writes `INTEGRATION.md` at the project root. It is a merge playbook for an AI
agent, not part of the project's runtime — nothing imports it, and it can be deleted once
the merge is done. It covers the two shapes a merge takes:

- **Mount into an existing server.** Copy `backend/core` and `backend/api-v1`, keep the
  destination's app and deployment, and add one `mount(app)` call. `backend/server` is not
  copied.
- **Merge the whole backend.** Copy all three backend packages into an existing monorepo
  and merge its workspace config and scripts.

The playbook also lists what cannot be inferred from the copied code: how to rename the
generic `core` / `api-v1` packages without missing the generator's own string literals, why
`core` and `api-v1` must be built before the host imports them, and which artifacts
(`src/api/**/index.*`, `docs/api.json`) must be regenerated rather than merged.

The file is opt-in because a standalone project does not need it, and a merge that starts
from a scaffold is a different job from one that starts from a code review. When you want
it later, scaffold again into an empty directory with the same flag.
