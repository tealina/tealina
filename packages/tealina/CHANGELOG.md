# tealina

## 3.0.0

### Major Changes

- 0f3fd92: Hand a handler template the directory its stub lands in, not a count of `../`

  `TemplateContext.relative2api` is gone, replaced by `fileDir`: the directory the generated
  file will be written into, spelled like `apiDir` — `src/api/post` for `tealina src/api
post/order` writing `src/api/post/order.ts`.

  The old field was a depth (`namePaths.length + 1`, the `+ 1` assuming `src/<api>` is two
  segments). Move the api directory one level deeper and every stub comes out one `../` short,
  and a config cannot repair that for itself — only the CLI knows where the file goes. So the
  CLI says where, and the config does the arithmetic:

  ```ts
  function generateBasicCode({ fileDir }: TemplateContext) {
    const from = (dir: string) => posix.relative(fileDir, dir);
    // `from('types')`, `from('src')` — this project's layout, stated by this project
  }
  ```

  The test templates move the same way: `genSuite` and `genHelper` receive `fileDir` instead of
  `relative2ancestor`. `apiDirName` and `typesDirName` are unchanged.

  **A config that reads `relative2api` stops working** — the property is `undefined`, so a
  concatenated specifier reads `undefined/access.js` and `node:path` throws. No alias is kept,
  because a number of `..` cannot stand in for a directory without reintroducing the
  assumption. The same goes for `relative2ancestor`. `create-tealina`'s templates are written
  against the new field from the same release, so the two move together.

- 0f3fd92: Move the api directory and URL prefix into the config, and fix the artifact names

  The api directory no longer has to be spelled in seven places. `tealina.config` supplies it:

  ```ts
  export default defineConfig({
    apiDir: "src/api",
    apiBaseURL: "/api/v1",
  });
  ```

  Every command reads it, so none takes a directory argument: `tealina create post/order`,
  `tealina delete post/order`, `tealina align`, `tealina gdoc`, `tealina gtype`. Both fields are
  required — `mergeInlineOptions` rejects a config without them — and neither is derivable from
  the other.

  The public artifacts keep fixed names regardless of `apiDir`: `types/api.d.ts`,
  `docs/api.json`, and `exports["./api"]`. Moving the directory therefore changes route
  discovery and handler imports, not what a frontend imports. `convertToOpenApiJson` takes the
  configured `apiBaseURL`, also handed to custom outputs as `GdocContext.baseURL`.

  `exclude` takes globs relative to `apiDir` (`['_shared/**', '**/*.test.ts']`), and
  `handlerImport: 'core/handler'` points generated stubs at a contract in another package; the
  default is still `./handler`.

  `create-tealina`'s templates are written for this release. Projects generated by an earlier
  version need the two required config fields before the new CLI can build them.

### Minor Changes

- 0f3fd92: Make the CLI's result machine-readable

  Three changes for callers that are programs rather than people:

  - `align` and `gdoc` accept `--check`: the same snapshot calculation, writes nothing, exits 1
    when a generated file is out of date.
  - Both accept `--json`, which prints one object on stdout and nothing else: `{ ok: true,
changed: [{ action, file }] }` for a normal run, `{ ok: false, changed: [...] }` for drift
    (or `{ ok: true, changed: [] }` when there is none). Errors go to stderr as `{ ok: false,
error: { message } }`; `--verbose` adds the stack.
  - Every error path now exits 1. Previously a failed `align` looked successful to a script.

  Generated files start with a two-line header naming the command that rebuilds them. The
  fallback `types/<api-dir>.d.ts` now exports `ApiTypesForDoc` and `ApiTypesForClient`; it
  referenced `ResolveApiType` / `ApiTypesRecord`, which do not exist, so it did not type-check
  and `gdoc` could not read it. `cli.version()` reads `package.json` instead of a hard-coded
  string.

  `--check` also exposed a bug: `parseDeclarationFile` kept its ref tables between calls, keyed
  by per-program type ids, so a second `gdoc` in one process could render a different document
  than the first. The tables are reset per call now.

- 0f3fd92: Spell `TealinaConfig`, `MatchForOptionalCheck` and `transformType` correctly

  Three public names have carried a typo since they were introduced, and are corrected without
  breaking an existing config file:

  - `TealinaConifg` → **`TealinaConfig`**, which `defineConfig` now takes.
  - `MatchForOptionalChcek` → **`MatchForOptionalCheck`**, the type of `gtype.overwrite.isOptional`.
  - `gtype.overwrite.transofrmType` → **`transformType`**.

  The old type names still resolve and are marked `@deprecated`. `transofrmType` is still read,
  but using it now prints a warning naming `transformType`; setting both resolves to
  `transformType`.

  The internal `getTestHeplerPath` becomes `getTestHelperPath`; deep paths are not in `exports`,
  so no alias was kept.

- 0f3fd92: Generate barrel keys as the logical path, and put the slash back at the router

  The generated `get/index.ts` reads `'health': import('./health.js')` instead of
  `'/health': ...`. `@tealina/server` prepends the slash in `transformToRouteOptions`, so a
  router still receives an absolute url — express refuses one that does not begin with `/`.

  **Upgrade the two together.** `align` regenerates a kind index from the file tree, so running
  it after this release rewrites every key to the new spelling — against an older
  `@tealina/server` the slash then never comes back and every route breaks. Upgrading the
  packages alone rewrites nothing (a barrel keeping `'/health'` still registers `/health`), so a
  project can migrate by running `align` when it is ready.

- 0f3fd92: Add `sourceExt`, and probe for a `.js` / `.mjs` tealina config

  `sourceExt` is the extension tealina gives the files it generates — the index files and the
  new handler stub. It defaults to `".ts"`, so an existing project sees no change; set it to
  `".js"` for a JavaScript project. It also reaches `TemplateContext`, so a `generateFn` can
  emit a JSDoc stub for a `.js` file, which is what lets the scaffolding template work without a
  second template tree.

  It is not the same option as `suffix`, which is what generated `import` statements say — under
  `moduleResolution: NodeNext` a TypeScript project writes `import './x.js'` and still names
  the file `x.ts`. Folding them into one knob would have renamed `index.ts` to `index.js` in
  every existing project.

  `--config-path` now probes `tealina.config.{ts,js,mjs}` when the caller did not name a file.
  An explicit path is still honoured exactly as given, even when it does not exist.

- 0f3fd92: Add a `tealina/utility-types` subpath, and let the scaffold take its types from there

  `tealina` already depended on `@tealina/utility-types`; it now hands those types to consumers
  from a types-only subpath — nothing to import at runtime, and the `exports` entry carries only
  a `types` condition.

  That lets a generated project drop a dependency: the contract layer (`types/handler.d.ts` and
  each framework's `types/alias.d.ts`) imported `@tealina/utility-types` directly, so every
  generated `server` package installed it a second time. Those imports name
  `tealina/utility-types` now, and the dependency is gone from all six template manifests.

  A subpath rather than the main entry on purpose: `tealina`'s root declaration re-exports
  `openapi-types` and reaches its own source through extensionless relative imports, which
  would tie the scaffold's compile to a build having run.

### Patch Changes

- 0f3fd92: Quote a generated key only when it is not an identifier

  A generated barrel reads `get: import('./get/index.js')` and `health: import('./health.js')`
  without quotes; `'user/:id'` and `'user/create'` keep theirs. That is a formatter's
  `quoteProps: 'as-needed'` judgement, so a barrel comes out as one would leave it, and the
  `align` after a formatting pass no longer rewrites it back.

- 0f3fd92: Require Node 22

  `vite-plus-core`'s tsdown calls `Promise.withResolvers`, which Node 20 lacks, so the build
  failed on the floor the packages claimed. `engines.node` is `>=22`, the Node-side `target` is
  `node22`, and `@types/node` is `^22`; CI and `.nvmrc` run the default Node 24.

  Node 20 is no longer supported. Nothing in the published API changed.

- 0f3fd92: Fix: the tsconfig's `compilerOptions` were silently dropped

  `gdoc` read the tsconfig and handed the whole object to `ts.createProgram`, so it landed in
  the `CompilerOptions` slot. TypeScript's guard against that shape hid it: every option —
  `allowJs`, `strict`, `paths`, `target` — was ignored and programs were built with defaults.
  It is parsed with `parseJsonConfigFileContent` now, which also resolves `extends`.

  That is what made a JavaScript project impossible to document: with no `allowJs`, a `.js`
  import does not resolve, `type RawApis = typeof apis` degrades to `any`, and the document came
  back empty with no error.

  Two visible consequences: the document no longer depends on `strictNullChecks` being off; and
  a module that resolves but exports no `default` now reports `Export symbol not found` instead
  of a `TypeError`.

  Fix: `gdoc`'s handler lookup looked through parentheses, and now does

  A JavaScript module cannot annotate a `const` holding an `async` function — the annotation is
  read as the function's own signature — so the cast goes on the expression:
  `const handler = /** @type {ApiType} */ (async (req, res) => {…})`. That is a
  `ParenthesizedExpression`, which the lookup did not accept, so every JS handler was reported
  as `Export default should be a function`. The lookup steps inside the parentheses now, and
  when the argument is not a name, says the fix is to cast a `const` and pass that const. For a
  TypeScript project this is an identity.

- 0f3fd92: Build with tsdown instead of unbuild

  `build.config.ts` is gone; `dist/` is packed by tsdown through `vite.config.ts` and `vp pack`.

  The output is deliberately the same: `src/` still mirrors 1:1 into `dist/` (tsdown's
  `unbundle`), so the bin shim's paths keep resolving, and declarations still come from
  `gen-types`. No change to `main`, `types`, `exports` or the file layout.

  Two things worth knowing, since the next package to move will meet them:

  - The `rollup.esbuild` block this replaces never did anything — `builder: 'mkdist'` never
    forwards `rollup`, so `target` and `minify` were inert. `target` is set explicitly now;
    minification stays off because `--verbose` prints execution stacks.
  - tsdown defaults `fixedExtension` to true for `platform: "node"`, giving `.mjs` — what the
    bin shim wants, but `dts: true` would emit `.d.mts` and miss `./dist/index.d.ts`.
    Declarations stay on `gen-types` for that reason.

  Published byte sizes change while the layout does not: rolldown is not a statement-preserving
  transpile, so it inlines and drops things — including the `// @ts-check` pragma in the file
  built from `src/utils/parseDeclarationFile.js`.

- 0f3fd92: Support TypeScript 6, and bound the peer range to it

  `typescript` is now `>=5.6.2 <7` rather than the open `>=5.6.2`. The old range was never read
  as "any future TypeScript": `gdoc` drives the compiler API, and 7.0 is a native rewrite
  without it, so an install resolving `latest` gets `ts.readConfigFile is not a function`.
  Nothing changes on 5.x or 6.x; past that, resolution now fails with a version in the message
  instead of a runtime error.

  Two build-side changes go with it:

  - `gen-types` passes `--ignoreConfig`, because it hands `tsc` a file list and 6.0 rejects that
    beside a `tsconfig.json` (TS5112) — what the command always meant.
  - It pins `--strict false`. 6.0 enables `strict` by default, and these declarations are
    published, so the flags describe the output already out there.

  One fix comes along: `gdoc` passed a relative config path to `createProgram` beside an
  absolutely-resolved source directory, tripping a TypeScript assertion in 6.0. The path is
  resolved first; which files are read does not change.
